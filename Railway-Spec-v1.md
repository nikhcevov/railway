# Railway — спецификация реализации

Версия: 1.0 Draft · 26 октября 2026.

Статус: предлагаемый контракт продукта и архитектуры на основе исходного черновика. Новые детали ниже — предлагаемые решения, а не ранее согласованные требования. Документ задаёт все пять этапов; первая реализация ограничена этапом 1 и обязательным техническим прототипом этапа 0.

## 1. Цель и пользовательский сценарий

Railway — серверный Fabric-мод для поездок по физически построенной ванильной железной дороге. Игрок подходит к кнопке с подписанным назначением, нажимает её правой кнопкой мыши и автоматически садится в появившуюся вагонетку. Вагонетка едет по рельсам, останавливается на станции назначения, игрок высаживается на платформу, вагонетка исчезает.

Обычному пассажиру не нужны команды, предметы, инвентарь вагонеток или клиентский мод. Одно нажатие выбирает назначение и запускает поездку, если она доступна. Если запуск невозможен, игрок получает понятное сообщение в action bar; скрытая очередь не создаётся.

Вагонетки служебные и бесплатные: мод создаёт их, не берёт из сундука, не выдаёт в предметах и удаляет без дропа. Сундуки-депо и экономика в 1.0 не входят.

## 2. Технический контракт

| Область | Решение |
| --- | --- |
| Название / mod ID | Railway / `railway` |
| Платформа | Minecraft Java Edition, Fabric Loader + Fabric API, Java |
| Среда | Dedicated server; обязательная проверка обычным клиентом той же версии |
| Игровые объекты | Только ванильные блоки и обычная пассажирская вагонетка |
| Клиентский протокол | Ванильные сообщения; обязательные custom payload и ресурс-пак отсутствуют |
| Администрирование | `/rail ...`, OP level 2 по умолчанию |
| Мир | Поддержка измерений раздельно, без маршрутов через порталы |
| Система сборки | Gradle Wrapper + Fabric Loom; конкретные версии зависимостей закреплены |
| Параллельность | Все обращения к миру, сущностям, блокировкам и изменения состояния — на серверном потоке |
| Совместимость | Отдельный артефакт под выбранную версию MC; произвольная версия не выбирается во время запуска |

Версия Minecraft — обязательный вход для первой сборки. До неё можно проектировать чистое Java-ядро, но нельзя фиксировать Minecraft API, mixin targets, Java toolchain и работоспособность движения. Поддержка нескольких версий не входит в первую поставку. Сначала проверяется фактический набор серверных модов и включённые экспериментальные механики вагонеток.

Мод не меняет физику пользовательских вагонеток. Изменения движения применяются только к сущностям, однозначно принадлежащим активным поездкам Railway.

## 3. Границы 1.0

Поддерживаются: пассажирские одиночные вагонетки, станции с одной платформой, выбор назначения отдельной кнопкой, пути в одном измерении, обычные и питающие рельсы, горизонтальные кривые и стандартные уклоны после проверки геометрии, переключаемые Т-развилки из обычных рельсов.

В первую версию не входят: составы, грузовые перевозки, расписание, билеты, GUI-карта, автоматическое строительство путей, телепортация вместо проезда, порталы, произвольные модовые рельсы, гарантия защиты от гриферства. Детекторные и активирующие рельсы первоначально отклоняются валидатором управляемого маршрута; их поддержку можно добавить отдельно с явной семантикой.

Крестовины с четырьмя направлениями, неоднозначные соседства и развилки на уклоне отклоняются. Визуальное соседство рельсов само по себе не означает проходимое соединение.

## 4. Станция и строительство

Минимальная станция содержит:

1. Прямой горизонтальный рельс остановки (`dock`).
2. Не менее двух прямых горизонтальных рельсов перед ним по направлению прибытия; этот участок нужен для финального выравнивания. Полная зона торможения может быть длиннее и вычисляется из скорости.
3. Безопасную платформу и заданную позицию высадки (`exit`).
4. Хотя бы одну кнопку назначения; табличка рядом служит подписью.

Позиция dock — центр блока рельса с поправкой на положение сущности выбранной версии MC. Остановка и отправление используют реальную геометрию пути, а не произвольное направление камеры игрока.

Dock должен иметь достаточно свободного места для пассажира. Exit задаёт блок ног и направление взгляда: твёрдая безопасная опора, свободные коллизии ног и головы, отсутствие лавы/огня и других проверяемых опасностей. Для 1.0 поддерживается обычная полноразмерная платформа; сложные коллизии полублоков и прочих блоков можно отклонять. Проверки повторяются непосредственно перед посадкой и высадкой.

MVP: две конечные станции на прямом горизонтальном участке без промежуточных станций и развилок. Допускается несколько отдельных таких линий. Dock на конце пути; вагонетка может отправиться в обратную сторону после новой поездки. Разворотная петля не требуется.

С этапа 2: маршрут определяет направление выхода из dock и направление въезда в него; на промежуточной станции вагонетка останавливается только если это назначение. Автоматические промежуточные остановки и пересадки не входят в 1.0.

Существующие обычные рельсы можно регистрировать; специальная текстура, обязательный маркер под каждым рельсом и перестройка мира не нужны. Неподходящая геометрия возвращает координаты ошибки.

## 5. Кнопка назначения

Binding хранит точный блок кнопки, станцию отправления и станцию назначения. Кнопка привязывается явно; в MVP близость таблички не определяет её назначение. Подпись на табличке не является идентификатором маршрута и не исполняет команды.

Запуск обрабатывается по взаимодействию конкретного игрока с кнопкой. Redstone-питание, стрела в деревянной кнопке и нажатие механизмом не создают поездку: они не задают пассажира.

Условия запуска:

- Кнопка зарегистрирована, существует и не была заменена блоком другого типа.
- Игрок жив, не spectator, не в другой машине и находится не далее `boardingRadius` от dock.
- Станции и путь доступны, scan завершён, резервирование успешно.
- Dock свободен от другой вагонетки и препятствий; место пассажира безопасно.
- У игрока нет активной поездки; лимиты сети и сервера не превышены.

Две руки, повторные пакеты и почти одновременные клики не создают дубликаты: проверка, резервирование, spawn и посадка выполняются как одна серверная операция с откатом при неудаче. После успешной посадки — короткая подготовка отправления. Если игрок успел выйти, поездка отменяется.

В MVP используется каменная кнопка; проверка запуска зависит от события взаимодействия, а не от состояния `powered`, чтобы корректно различать игроков. Cooldown применяется к игроку, а не ко всей станции.

## 6. Модель данных

| Сущность | Основные поля и инварианты |
| --- | --- |
| Station | `id`, `displayName`, `dimension`, `dock`, `exit`, `exitYaw`, `enabled`, `revision`; один dock, ID уникален в мире |
| Binding | `id`, `dimension`, `buttonPos`, `expectedButtonType`, `fromStationId`, `toStationId`; один binding на кнопку |
| RailGraph | `dimension`, `revision`, топология, порты соединений, разрешённые переходы, зависимости от блоков; производный кэш |
| RoutePlan | `graphRevision`, станции, упорядоченные проходы рельсов, требуемые состояния стрелок, длина; неизменяемый результат планирования |
| Trip | `id` UUID, `playerUuid`, `cartUuid`, станции, `routePlan`, фаза, checkpoint, причина завершения |
| Reservation | владелец `tripId`, набор ресурсов, стадия захвата/освобождения; runtime-состояние |

Публичные ID станций: `[a-z0-9_-]{1,32}`, например `home`, `mine`. Отображаемые имена могут быть русскими. UUID поездки отличается от UUID сущности. Ссылка на блок всегда включает измерение.

## 7. Граф и маршрутизация

Граф строится по физическим рельсам, их высоте, типу и допустимым переходам. Ключ состояния поиска включает рельс и направление входа: одного соседства блоков недостаточно для проверки реального проезда через стрелку.

Разделяются:

- Постоянная топология: какие переходы физически допустимы при разрешённых положениях рельса.
- Текущее состояние стрелки: какая пара портов соединена сейчас.
- Занятость: кем зарезервирован участок.

Обычный горизонтальный рельс может участвовать в переключаемой Т-развилке; питающий рельс не считается кривой или стрелкой. Не перечисляются все соседние рельсы как взаимно достижимые: каждый переход проверяется на допустимую форму и соседние высоты.

Первый алгоритм — Dijkstra по длине пути в блоках; при равной длине выбирается стабильный порядок координат. Оптимизация по времени и сложные штрафы не нужны. Пересадки не планируются. Поиск возвращает путь либо структурированную причину отказа; его бюджет ограничен.

Сканирование работает порциями по тикам и не загружает произвольный объём мира за один tick. Неизвестный или не загруженный участок означает «scan неполон», а не «пути нет». Пределы сканирования и чтения чанков явные. Сканирование может временно загружать только уже созданные чанки в пределах бюджета; генерация нового мира запрещена. В MVP scan требует загруженной линии.

Установка/слом/изменение рельсов инвалидируют затронутый граф. Перед стартом и при подходе к следующему участку выполняется повторная проверка. Для активной поездки самовольная смена маршрута не выполняется: она останавливается и завершается аварийно либо продолжает после подтверждённого восстановления той же геометрии. Новый путь рассчитывается для следующей поездки.

## 8. Стрелки и резервирование

Этапы 1–2: одна активная поездка на связную компоненту сети; независимые компоненты работают параллельно. Это консервативная защита от взаимных конфликтов, а не модель пропускной способности конечного релиза. При неизвестной границе компоненты отправление запрещено.

Этап 3: сеть делится на эксклюзивные ресурсы — однопутные перегоны между станциями/стрелками, конфликтные зоны стрелок и платформы. На поездку атомарно резервируются все ресурсы маршрута до spawn. Захват «всё или ничего» исключает взаимную блокировку поездок. Ожидание отсутствует: занятый маршрут возвращает «Путь занят, попробуйте позже». Независимые маршруты могут ехать одновременно; следование нескольких вагонеток внутри одного перегона не поддерживается.

Ресурсы маршрута освобождаются после завершения или отмены поездки и удаления/остановки служебной сущности. При сомнении в положении вагонетки ресурсы карантинируются до сверки, а не выдаются следующей поездке.

Перед проездом стрелка выставляется под требуемый переход и проверяется повторным чтением block state. Мод удерживает управление до выхода вагонетки из конфликтной зоны. Redstone и обновления соседей не должны незаметно перекинуть стрелку под пассажиром: при несовпадении — остановка до зоны конфликта. Бесконечное переключение в одном tick не допускается. После освобождения стрелка остаётся в последнем валидном положении; восстановление её старой формы не обещается.

## 9. Движение и скорость

Поездка использует ванильную сущность и реальное движение по рельсам. Постоянная телепортация по точкам не является допустимой заменой.

| Параметр | Предлагаемое значение |
| --- | --- |
| Целевая скорость после этапа 3 | 12 блоков/с на прямой при 20 TPS |
| MVP | Проверенная ванильная скорость выбранной версии, без обещания 12 блоков/с |
| Ускорение | 4 блока/с², настраивается |
| Рабочее торможение | 6 блоков/с², настраивается |
| Кривые и уклоны | Отдельные подтверждённые испытаниями ограничения; исходный кандидат 4 блока/с |
| Точность остановки | Не далее 0,25 блока от центра dock, нулевая скорость перед высадкой |

Значения скорости — проектные цели до прототипа, а не подтверждённые возможности всех MC-версий. Внутри движение считается по игровым тикам; при падении TPS реальное время поездки увеличивается, компенсация скачком скорости запрещена.

Расстояние для торможения: минимум `v² / (2a)` плюс запас на один tick движения и `safetyMargin`. При 12 блоках/с и торможении 6 блоков/с² основа составляет 12 блоков. Ограничение скорости учитывает ближайшую кривую, уклон, конец разрешённого участка, препятствие и dock. Короткий путь просто не достигает максимальной скорости.

Railway обеспечивает тягу служебной вагонетки: powered rails не обязательны. Их питание не отменяет команду остановки. Движение по уклонам и кривым обязательно проверяется отдельно с обычным клиентом.

Резервации защищают от других управляемых поездок. Свободные ванильные вагонетки, мобы и изменяемый игроками мир требуют отдельного контроля препятствий. При известной опасности впереди вагонетка тормозит; внезапное появление блока прямо внутри неё не покрывается гарантией предотвращения любого ущерба.

## 10. Жизненный цикл и ошибки

Основные фазы: `PREPARING → BOARDING → RUNNING → ARRIVING → COMPLETED`.
Из любой активной фазы возможны `ABORTING → ABORTED`. После загрузки мира используется отдельная фаза `RECOVERING`, не позволяющая новым поездкам занять ещё не сверенные ресурсы.

Инварианты:

- Не более одной активной поездки на игрока и одной управляемой вагонетки на поездку.
- Только пассажир, нажавший кнопку, назначается в поездку.
- Вагонетка не отправляется до успешной посадки и получения всех ресурсов.
- Удаление вагонетки с сидящим игроком выполняется только после высадки/безопасного завершения.
- Ни один путь ошибки не создаёт предмет вагонетки и не удаляет чужую сущность.

| Событие | Поведение |
| --- | --- |
| Нет пути, сеть занята, станция выключена | Сообщение игроку; вагонетка не создаётся |
| Spawn или посадка не удались | Удалить созданную пустую вагонетку, освободить ресурсы, вернуть ошибку |
| Игрок нажал Shift | Позволить ванильный выход; остановить и убрать пустую служебную вагонетку, завершить поездку |
| Игрок отключился/умер/был телепортирован | Отменить поездку; остановить и сверить сущность; не продолжать поездку без пассажира |
| Финиш | Полная остановка, проверка exit, высадка, удаление вагонетки без дропа, освобождение ресурсов |
| Exit заблокирован | Остановиться с пассажиром, сообщить проблему; попытаться найти безопасное место рядом в радиусе 3 блоков; при неудаче оставить возможность ручного выхода, удерживать платформу |
| На линии сломан рельс или неизвестный участок впереди | Торможение до опасного участка, сообщение и аварийное завершение с безопасной высадкой, когда она возможна |
| Неизвестный исход удаления/выгрузка сущности | Карантин ресурсов и сверка перед следующим отправлением |
| Таймаут поездки | Перевод в аварийное завершение; таймаут не разрешает высадку в опасное место или освобождение занятого пути |

При выходе игрока посреди пути Railway не телепортирует его обратно на станцию. Экстренная высадка при остающемся пассажире использует проверенную ближайшую безопасную позицию; если такой нет, вагонетка остаётся остановленной, диагностика требует вмешательства администратора. Защита от ручного Shift и падения игрока в построенном над пропастью пути не обещается.

## 11. Чанки, сохранение, перезапуск

Безопасность жизненного цикла реализуется с этапа 1. Этап 5 расширяет её на длинные маршруты, crash recovery и эксплуатационную диагностику.

MVP: поездки только по загруженным и тикающим участкам; перед отправлением проверяется весь маршрут. Проверка повторяется впереди движущейся вагонетки; запрет движения в неготовый участок действует уже в MVP.

Этап 5: ограниченные chunk tickets удерживают текущую позицию и окно впереди, рассчитанное минимум на тормозной путь. До готовности следующего окна вагонетка останавливается. Загрузка не означает готовность тика сущности: адаптер проверяет нужный уровень готовности. Tickets освобождаются по завершении; весь маршрут постоянно загруженным не удерживается. Новые чанки мод не генерирует.

Хранение:

- `config/railway.json`: настройки с `configVersion`, проверкой диапазонов и диагностикой ошибок.
- Состояние внутри папки конкретного мира: станции, bindings, `schemaVersion`, монотонная revision.
- Граф и маршруты — производные данные; после запуска пересоздаются/валидируются.
- Служебная вагонетка — обычная сущность с сохраняемым маркером принадлежности и `tripId`; конкретный способ выбирается под MC-версию.
- Checkpoint активной поездки содержит минимальные данные для сверки, но не считается доказательством фактического положения сущности после crash.

После перезапуска поездки автоматически не продолжаются. Сначала Railway сверяет checkpoints и помеченные сущности при загрузке чанков, безопасно завершает оставшиеся поездки, убирает пустые сиротские вагонетки и лишь затем открывает затронутые ресурсы. Игроку с незавершённой поездкой при входе выполняется сверка положения; телепортация в неподтверждённый exit запрещена. Повторная сверка идемпотентна. Несогласованное сохранение файла мира и данных Railway не должно приводить к размножению вагонеток или удалению пользовательских вагонеток.

Минимум MVP: чистый restart не оставляет работающих поездок, checkpoints позволяют обнаружить прерванное состояние, новые отправления закрыты до сверки известного маршрута. Расширенное восстановление после аварии и поздней загрузки чанка — обязательный критерий этапа 5.

Невалидный конфиг не переписывается дефолтами. Ошибка критических настроек выключает Railway с диагностикой, не должна останавливать загрузку всего Minecraft-сервера. Миграции данных версионируются; перед миграцией создаётся резервная копия. Reload меняет параметры только для новых поездок; активная использует снимок настроек. Изменения, требующие restart, явно отклоняются при reload.

## 12. API команд

Синтаксис ниже — предлагаемый публичный API. Идентификаторы в `<...>` — аргументы, `[... ]` — необязательные. Команды следующих этапов не должны возвращать фиктивный успех до реализации.

| Команда | Семантика | Этап |
| --- | --- | --- |
| `/rail help` | Доступные команды и подсказки | 1 |
| `/rail station create <id> <displayName...>` | Создать станцию по рельсу под прицелом, дальность 5 блоков; изначально выключена | 1 |
| `/rail station exit <id>` | Задать exit по текущей позиции ног и yaw администратора после проверки | 1 |
| `/rail station rename <id> <displayName...>` | Изменить только отображаемое имя | 1 |
| `/rail station enable <id>` | Включить после проверки обязательных полей | 1 |
| `/rail station disable <id>` | Закрыть новые отправления и прибытия; при активной поездке к/от неё отклонить и предложить сначала abort | 1 |
| `/rail station info <id>` | Координаты, состояние, ошибки, bindings | 1 |
| `/rail station list` | Список станций | 1 |
| `/rail station remove <id>` | Удалить вместе с bindings к/от неё; отказ при активной поездке; мир не меняется | 1 |
| `/rail button bind <from> <to>` | Привязать кнопку под прицелом, дальность 5 блоков | 1 |
| `/rail button info` | Binding кнопки под прицелом | 1 |
| `/rail button unbind` | Удалить binding кнопки под прицелом | 1 |
| `/rail network scan <station>` | Запустить ограниченный scan от dock; вернуть ID задания | 1 |
| `/rail network status [station]` | Статус scan, revision, полнота сети, ошибки | 1 |
| `/rail route check <from> <to>` | Проверить путь без spawn/резервирования; длина и причины отказа | 1 |
| `/rail trip list` | Активные и восстанавливаемые поездки | 1 |
| `/rail trip abort <tripId>` | Безопасно остановить и завершить; может остаться в ABORTING без безопасной высадки | 1 |
| `/rail reload` | Валидировать и применить настройки; при ошибке оставить прежние | 1 |
| `/rail diagnostics [station]` | Геометрия, занятость, стрелки, лимиты, проблемы tickets | 5 |

MVP scan и route check понимают только прямую горизонтальную линию. Они отклоняют неподдерживаемую геометрию с координатами. Это сохраняет API без обещания маршрутизации этапа 2.

Команды изменения и управления — OP level 2. Пассажиру OP не нужен. Команды с прицелом/текущей позицией доступны только игроку; консоль получает ясную ошибку. Списки, info, scan по ID, reload и abort могут запускаться из консоли. Поддерживается автодополнение ID и диагностические коды; человекочитаемое сообщение сопровождает каждый отказ. Chat-click команды и выполнение текста табличек не используются.

Пример настройки двух станций:

1. Глядя на dock: `/rail station create home Дом`.
2. Стоя на платформе: `/rail station exit home`.
3. `/rail station enable home`.
4. Аналогично создать `mine`.
5. У кнопки дома: `/rail button bind home mine`.
6. У кнопки шахты: `/rail button bind mine home`.
7. `/rail network scan home`, дождаться завершения, `/rail route check home mine`.
8. Обычный игрок нажимает кнопку у подписи «Шахта».

Ручной команды поездки в пассажирском сценарии нет. Сохранённые маршруты и их ID не нужны: binding задаёт пару станций, путь вычисляется по текущему графу.

## 13. Настройки и ограничения ресурсов

Исходные значения — стартовые настройки для небольшого частного сервера, уточняемые испытаниями:

| Ключ | Значение | Назначение |
| --- | --- | --- |
| `boardingRadius` | 4 блока | Допустимая близость пассажира к dock |
| `boardingDelayTicks` | 10 | Подготовка после посадки |
| `playerCooldownTicks` | 20 | Защита от повторных взаимодействий |
| `maxActiveTrips` | 8 | Общий предел сервера, с учётом более строгих ограничений этапов |
| `maxSpeed` | 12 блоков/с | Используется после подтверждения этапа 3 |
| `acceleration` / `braking` | 4 / 6 блоков/с² | Плавность движения |
| `safetyMargin` | 2 блока | Добавка к расстоянию торможения |
| `maxRailsPerScan` | 50 000 | Жёсткий предел обхода одного задания |
| `scanRailsPerTick` | 250 | Верхняя граница работы scan за tick |
| `scanTimeBudgetMs` | 2 мс | Дополнительный временной бюджет; действует первым достигнутый предел |
| `maxRouteLength` | 10 000 блоков | Ограничение маршрута |
| `maxManagedChunkTickets` | 128 | Общий предел собственных tickets scan и поездок |
| `maxTripTicks` | 36 000 | Таймаут 30 игровых минут; перевод в аварийное завершение |
| `builders` | `[]` | Необязательный список UUID игроков, которым разрешена регистрация табличек; OP level 2 разрешён всегда. Невалидный UUID или дубликат делают конфиг невалидным; ключ не меняет `configVersion` |

Достижение бюджета возвращает `LIMIT_EXCEEDED`/`SCAN_INCOMPLETE`/`CHUNKS_NOT_READY`, не частичный успешный маршрут. Для MVP автоматические tickets поездок не используются. Неизвестные параметры и неверные диапазоны диагностируются. Настройки сериализуются с единицами, описанными в документации.

## 14. Строительство без команд — этап 4

«Без админ-команд» означает разрешённый способ регистрации по ванильным табличкам, а не автоматическое угадывание намерений по декоративной постройке.

Шаблон станции: настенная табличка на опорном блоке dock, сам dock непосредственно сверху этого блока. Строки:

```text
[Railway]
home
Дом
station
```

При сохранении таблички уполномоченным строителем мод проверяет шаблон, ID и dock. Безопасный exit ищется среди соседних блоков платформы на том же уровне в фиксированном порядке N/E/S/W; выбранный блок подсвечивается краткими ванильными particles и показывается в сообщении. Если места нет — регистрация отклоняется с объяснением. Для точного выбора остаётся `/rail station exit`.

Шаблон назначения: настенная табличка и каменная кнопка на разных горизонтальных гранях одного опорного блока в радиусе 4 блоков от dock. На блоке должна быть ровно одна такая кнопка и одна служебная табличка. Строки:

```text
[Railway]
home
mine
go
```

Регистрация происходит после редактирования таблички; если кнопки ещё нет, игрок ставит кнопку и повторно сохраняет табличку. Неоднозначный шаблон отклоняется. Мод может заменить видимый текст назначения отображаемым именем, только на зарегистрированной служебной табличке, сохраняя binding в данных.

По умолчанию регистрировать станции таким способом может только OP level 2; на частном сервере можно включить явный список UUID строителей. Рядовой пассажир пользуется готовой станцией. Произвольные тексты табличек и постройки игроков не регистрируются, произвольный код и команды из текста не выполняются.

Разрушение служебной таблички/кнопки отключает соответствующую регистрацию; dock или станционная платформа при этом не удаляются. Изменение ID с существующими зависимостями отклоняется: нужен явный новый объект. Перемещение маркеров поршнями не поддерживается и приводит к инвалидизации после проверки.

## 15. Архитектура кода

Один Gradle-проект, без преждевременного разбиения на множество модулей:

| Пакет / компонент | Ответственность |
| --- | --- |
| `domain` | Station, Binding, Trip, RoutePlan, состояния и ошибки; без Minecraft-классов |
| `network` | Scanner, геометрия/порты, граф, Dijkstra, invalidation |
| `dispatch` | Проверки, резервирование, запуск и завершение поездок |
| `motion` | Скоростной профиль, торможение, контроль маршрута |
| `minecraft` | Fabric callbacks, чтение мира, spawn/mount/dismount, chunk readiness, mixins |
| `commands` | Brigadier, OP-проверки, человекочитаемая диагностика |
| `persistence` | World state, checkpoints, schema migration, config |

Чистое ядро оперирует собственными типами координат и идентификаторов. Minecraft-адаптер переводит их в API выбранной версии. Контракты адаптеров: `WorldAccess`, `CartControl`, `PassengerControl`, `ChunkAccess`, `StateStore`; они не обязаны быть отдельными внешними библиотеками.

Mixin — только там, где callback/API не хватает; каждый hook документирует задачу и ограничение только служебными вагонетками. Названия Minecraft методов фиксируются после выбора MC/mappings. Граф можно считать на immutable snapshot, но первая версия выполняет scan по тикам на серверном потоке; фоновые обращения к миру запрещены.

## 16. Поставка и критерии приёмки

### Этап 0 — технический прототип

- Зафиксировать MC, Loader, Fabric API, Loom, mappings, JDK и серверные моды.
- Поднять dev dedicated server и подключить обычный клиент.
- Одним взаимодействием создать ванильную вагонетку, посадить игрока, проехать, остановиться и безопасно высадить.
- Проверить кандидат 12 блоков/с, направление в обе стороны, уклон, кривую, плавность на клиенте; неподтверждённые параметры не переносить в обещания релиза.
- Проверить переключение Т-стрелки при redstone и neighbor updates.
- Результат: короткий технический отчёт с выбранными API/hooks и известными ограничениями. При проблемах server-only движения согласовать изменение требования до основного движка.

### Этап 1 — станции и полный MVP-сценарий

- Две конечные станции, прямая горизонтальная линия, отправление в обе стороны.
- Команды этапа 1, bindings, scan, минимальное world state.
- Одно нажатие → одна вагонетка → автопосадка → поездка → остановка → высадка → удаление без предмета.
- Проверены Shift, disconnect, отказ посадки, занятый dock, две руки/двойной клик, два игрока одновременно, сломанный путь, небезопасный exit и чистый restart.
- Не менее 20 последовательных поездок в обе стороны без накопления сущностей и блокировок.
- Обычные пользовательские вагонетки ведут себя как прежде.

### Этап 2 — маршруты и стрелки

- Граф с состоянием входа, Dijkstra, проверка геометрии и invalidation.
- Т-образная сеть с тремя станциями: каждая разрешённая пара достижима, вагонетка проходит правильную ветку.
- Проверены кривые, уклоны, тупик, цикл, отсутствие маршрута, неоднозначное соединение, powered rail на месте предполагаемой стрелки, изменение пути после scan.
- Смена состояния стрелки извне обнаруживается до конфликтной зоны.

### Этап 3 — движение и параллельные поездки

- Подтверждённые 12 блоков/с на прямой, ускорение, торможение, ограничения кривых/уклонов.
- Два встречных запроса общего пути: запускается только один.
- Два независимых маршрута запускаются параллельно.
- Конфликтующие платформы/стрелки эксклюзивны; нет deadlock при атомарном захвате.
- Проверены короткий путь, въезд на станцию с максимальной скорости, препятствие и корректное поведение при снижении TPS.

### Этап 4 — регистрация строительством

- Приведённые шаблоны создают станцию и binding без slash-команд.
- Проверены права строителя, дубли ID, неверные назначения, сломанные маркеры и неоднозначная геометрия шаблона.
- Ошибки видны в игре, чужие декоративные таблички не затрагиваются.

### Этап 5 — эксплуатация

- Длинный маршрут за пределами simulation distance с ограниченными tickets.
- Чистый restart и принудительное завершение процесса в разных фазах поездки.
- Поздняя загрузка чанка с сиротской вагонеткой, повторное восстановление, несовпадение checkpoint и entity state.
- Нет дубликатов/потерь пользовательских вагонеток и бесхозных Railway tickets после завершения восстановления.
- Диагностика показывает активные поездки, занятость, revision, задания scan, tickets, причины отказов.
- Проверка на реальной сборке серверных модов и удаление Railway на резервной копии мира.

Unit-тесты: направленные переходы графа, путь, резервирование, state machine, скоростной профиль и миграции. Серверные интеграционные/GameTest проверки — где поддерживает выбранная версия. Обычный клиент обязателен для проверки движения, автопосадки и высадки; одни unit-тесты не подтверждают server-only UX.

## 17. Удаление мода и совместимость

Railway не регистрирует собственные типы блоков/предметов/сущностей. Без мода рельсы, кнопки и таблички остаются ванильными; стрелки сохраняют последнее положение. Автоматика прекращает работать. Служебная вагонетка, оставшаяся после аварийного удаления мода, может остаться обычной ванильной сущностью; обещания автоматической очистки без установленного Railway нет.

Штатное удаление: закрыть отправления, завершить активные поездки, убедиться в отсутствии служебных сущностей, остановить сервер, сохранить резервную копию и убрать jar. Данные Railway можно оставить — ванильный мир их не использует.

Совместимость с любыми оптимизаторами и модами движения не предполагается автоматически. Для первой сборки составляется список фактически проверенных версий. Существующие пользовательские redstone-стрелки на управляемых маршрутах должны быть переданы под управление Railway или отклонены как конфликтная схема.

## 18. Что требуется перед первым коммитом реализации

Обязательные факты от сервера: точная версия Minecraft, версия Fabric Loader, список модов и версии, включённые эксперименты вагонеток. Для проверки нужен отдельный тестовый мир/копия, не рабочий мир.

Предлагаемые продуктовые defaults, с которыми можно начинать без дополнительных развилок: одна платформа на станцию; кнопка на каждое назначение; автоматическая посадка; бесплатная служебная вагонетка; без очередей; резервирование всей компоненты в MVP и всех ресурсов пути с этапа 3; ручная регистрация в MVP; без порталов и грузов.

Порядок первой реализации: toolchain → прототип server-only движения → domain и world state → station/button commands → scanner прямой линии → атомарный dispatch → полная поездка и ошибки → клиентская приёмка MVP. Этапы 2–5 не должны блокировать поставку первого работающего сценария.
